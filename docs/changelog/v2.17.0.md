# v2.17.0 — 2026-09-07

**Type:** feat
**Scope:** harness

Signal generation. `/today` shipped in v2.16.0 as a working screen with no source of input;
this is the job that fills it. Runs as `signal_sweep` every 4 hours, or on demand via
`POST /api/signals/generate`.

**Why:** the previous daily digest was a prompt-cron job that wrote prose into a chat
conversation — it told you what needed attention and then made you go do all of it by hand in
other screens. v2.16.0 made signals first-class objects you can act on where you read them, but
nothing was creating them. This closes that loop.

Decisions worth recording:

- **Detectors split by fact vs judgement.** A calendar double-booking, a stalled task, and an
  action item with no linked task are *facts* — computable with a comparison operator. Sending
  those to a model would be slower, cost money, and be less reliable. Only genuine judgement
  ("did I commit to something in this transcript?") goes to the model, on Tier 2 with a strict
  JSON contract and a prompt explicitly told that an empty array is a correct and common answer.
- **Action items are grouped by meeting, not one card per item.** This one was decided by real
  data rather than taste: a single week of Mike's meetings produced **225** unconverted action
  items. As individual cards that is not a triage surface, it is a wall. Grouped, 225 became 18,
  and "16 action items from the VIP Automotive meeting were never assigned" is one decision
  rather than sixteen.
- **`dedupe_key` is checked against signals in any status, not just open.** So something
  dismissed never comes back. The trade is explicit: a dismissed-but-still-true condition (a
  task that stays stalled) stays dismissed. Re-surfacing it would be technically correct and
  would still be wrong — re-nagging is how a triage surface loses trust.
- **A per-sweep cap of 12**, sorted most-urgent-first, so one pathological day cannot produce a
  hundred cards. Anything cut is reported as `deferred_by_cap` rather than silently dropped.
- **Sweep results distinguish `created` / `already_seen` / `deferred_by_cap`,** and surface
  `model_errors`. An earlier version conflated the first three into one number and swallowed
  model failures, which meant a misconfigured tier looked exactly like "nothing to report".
- **Reasoning text only claims what was actually checked.** An earlier draft of the commitment
  detector wrote "No matching task, To-Do, or sent email exists" — nothing verified that. A
  reasoning line that asserts unverified facts undermines the entire point of showing the work.

**Bugs found while testing against real data:**

1. `core/model_client._resolve_pair` hardcoded `"glm-4.7"` as the tier2 fallback model
   regardless of provider. With the default `tier2_provider = "anthropic"` and no model
   override, that sent a Z.ai model name to the Anthropic API, which 404'd **every** Tier 2
   request — silently breaking all of Tier 2, not only this generator. Now provider-appropriate.
   Worth checking production's tier2 settings; an install with `tier2_provider=zai` and a key
   set was unaffected.
2. User resolution used `User.name`, but the canonical row matches on `User.id` — the pattern
   hardened in v2.15.10 after the duplicate-ingestion incident. Fixed in the generator and in
   `scripts/seed_signals.py`.

**Verified** against real local data: 18 grouped meeting signals and 4 extracted commitments
carrying verbatim quotes, from actual AA Law, TenderBites, and LickSleeve meetings.

**No schema change** — harness-only deploy.
